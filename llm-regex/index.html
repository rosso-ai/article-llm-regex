構造化出力における正規表現の活用と有効な場面

はじめに

LLMに決まった形式で出力させたいとき、いまは構造化出力（Structured Output）を使うのが当たり前になりました。JSON Schemaを渡せば、返ってくるJSONのキーや型が保証される。私はこの機能のおかげで様々な開発がずいぶん楽になりました。

ところで、構造化出力では正規表現も使えるのをご存知でしょうか？私はついさっき知りました。

今回は、構造化出力での正規表現で何ができて、どのような場面で有効なのかを検証してみます。

検証には2つのモデルを使います。ローカル代表の Qwen3.6-27B（vLLM で自宅サーバーに立てたもの）と、クローズド代表の gpt-5.6-sol（OpenAI）です。同じお題を両方に出して、正規表現あり/なしでどう変わるかを見ていきます。

……と、ここまでの検証を一通り書き上げて、AIデータ分析技術部のリーダーのレビューを待っていたら、OpenAI から新しいモデル（GPT-6系）が出てしまいました。そこで OpenAI 側の検証は、新しい gpt-6.1-sol と、小型モデルの gpt-5.6-luna でも取り直しました。以降は 5.6-sol・6.1-sol・luna と略し、前回の 5.6-sol の結果も並べて載せます。

制約付きデコードの仕組みと各環境での指定方法

仕組みは「制約付きデコード（constrained decoding）」と呼ばれます。正規表現を状態機械（オートマトン）に変換し、トークンを1つ生成するたびに「その正規表現をまだ満たせる候補」以外の確率をゼロにします。だから正規表現に一致しない出力は最初から生成されません。プロンプトでお願いする場合と違って破れないのは、これが理由です。

使い方は推論サーバーによります。今回は vLLM（Qwen3.6-27B を動かしているサーバー）を使いました。リクエストに structured_outputs を足すだけです。

python
body = {
    "model": "Qwen/Qwen3.6-27B",
    "messages": [{"role": "user", "content": "適当な携帯番号を1つ"}],
    "structured_outputs": {"regex": r"0[789]0-\d{4}-\d{4}"},
}

これで返ってくるのは 080-1234-5678 のように、必ず正規表現通りの文字列になります。

OpenAIの場合は2通り

OpenAI 側はどうか。調べると2通りありました。

ひとつめは JSON Schema の pattern です。2025年から使えるようになっていて、文字列フィールドに書くだけ。

json
{
  "type": "object",
  "properties": {
    "phone": { "type": "string", "pattern": "^0[789]0-\\d{4}-\\d{4}$" }
  },
  "required": ["phone"]
}

しかもこれは、出力した後にチェックしているだけではなく、生成のその場で本当に縛っているようでした。試しに「2+2は？」と聞きながら、答えを ^Z{10}$（Zを10個）に強制してみると、ZZZZZZZZZZ が返ってきます。意味を捨ててでも形式を満たしにくる（6.1-sol・luna でも同じでした）。

ただし今回試した範囲では、この pattern は簡易版のようです。複数行にまたがる正規表現（あとで出てくる俳句の五七五のような形）を渡すと、1行目だけ出して止まってしまい、強制になりませんでした。これも 6.1-sol・luna で変わりませんでした。

複雑な正規表現には、ふたつめの Responses API の Custom Tool ＋ grammar を使います。「ツールの入力形式」として正規表現を渡す形で、こちらは複数行でもきちんと強制できました。

python
tools=[{
    "type": "custom",
    "name": "submit",
    "description": "結果を提出する。",
    "format": {"type": "grammar", "syntax": "regex", "definition": pattern},
}],
tool_choice={"type": "custom", "name": "submit"},

sol のような推論モデルで使うときの注意が3つあります。①推論トークンだけで出力の上限を使い切らないよう max_output_tokens を多めに確保する、②reasoning.effort は低めで十分、③結果は本文ではなく custom_tool_call の input に入る、の3点です。私は最初これを知らず、「複数行の正規表現を渡すと応答が返ってこない」としばらくハマりました。

というわけで、ローカル（vLLM）でもクローズド（OpenAI）でも、正規表現で出力を縛ること自体はできます。ここからは実際にいろいろ試していきます。

どんなことができるか

まずはローカルの Qwen 側で、いくつかの正規表現で強制してみます。

  • 携帯番号 0[789]0-\d{4}-\d{4} → 080-1234-5678
  • プライベートIP 192\.168\.\d{1,3}\.\d{1,3} → 192.168.0.100
  • 複数行のテンプレ穴埋め（名前: 〇〇\n年齢: 〇〇歳\n職業: 〇〇）→ 決まった行構成で埋まる

日付やUUIDのような形式も同じように書けます。

python
# 携帯番号を強制する構造化出力の指定
pat = r"0[789]0-\d{4}-\d{4}"
 
# vLLM
body["structured_outputs"] = {"regex": pat}
 
# OpenAI（JSON Schema の pattern に入れる）
{"type": "string", "pattern": f"^{pat}$"}

構造化データの量産

繰り返しを組み合わせると、決まった形式のデータをまとめて作れます。たとえばタイムコード付きの字幕を、1回のリクエストで。正規表現は「1行1キューを8〜12回」と書くだけです。

python
# 1行1キュー（時刻 --> 時刻 | 字幕）を8〜12回くり返す
sub = r"(?:\d{2}:\d{2}\.\d{3} --> \d{2}:\d{2}\.\d{3} \| [^\n]{1,40}\n){8,12}"
 
# vLLM
body["structured_outputs"] = {"regex": sub}
 
# OpenAI（改行を含む複数行 → pattern では効かず grammar を使う）
{"type": "grammar", "syntax": "regex", "definition": sub}

これで返ってきたのがこちらです。

21:45.000 --> 21:47.500 | 警告！ 重力シールドが崩壊しました。
21:47.500 --> 21:50.000 | 全員、避難経路Cへ移動せよ！
21:50.000 --> 21:52.500 | 待て！ 船体の構造が耐えられない！
...

面白いのは、正規表現は各行の時刻を独立に許しているだけなのに、モデルが自分で前の行の終了時刻を次の開始時刻につなげ、しかも全体を1つのシーンとして話を通したことです。形式を固定しても、中身の文脈までおかしくなるわけではありません。パース不要の構造化データを、まとめて作れます。

ここまでは、正規表現の構造化出力の「強さ」がそのまま出ています。

正規表現による構造化出力の限界

正規表現は強力ですが、万能ではありません。試すうちに、はっきりした限界がいくつか見えました。

「各種1文字以上」は書けない

パスワードを作らせたくて、「大文字・小文字・数字・記号をそれぞれ1つ以上含む」という条件を正規表現にしようとしました。

^(?=.{8,16}$)(?=.*[A-Z])(?=.*[a-z])(?=.*[0-9])(?=.*[!@#$%])(?!.*(.)\1)[A-Za-z0-9!@#$%]+$

ところがこれはエラーで弾かれます。制約付きデコードのエンジンは、処理速度を保つために正規表現の先読み（lookaround）に対応していないようです。

これは OpenAI でも同じでした。ただし失敗のしかたが、検証の途中で変わりました。最初に 5.6-sol で試したときは、pattern に先読みを渡してもエラーにならず黙って無視され、制約のかかっていない普通の出力が返ってきました。気づきにくいぶん、怖い挙動です。

ところが GPT-6系の検証のときに試し直すと、OpenAI も vLLM と同じく400エラー（regex lookaround is not supported）を返しました。5.6-sol に同じリクエストを送り直しても400だったので、変わったのはモデルではなく API 側のようです。黙って無視されるよりは、弾いてもらえるほうが気づけます。

正規表現で確実に書けるのは「使ってよい文字の種類」と「長さ」まで。「どこかに必ず大文字を1つ」のような条件は、どちらの環境でも表現できませんでした。

python
# 実際に効かせられるのは「文字種＋長さ」だけ
pat = r"[A-Za-z0-9!@#$%]{8,16}"
 
# vLLM
body["structured_outputs"] = {"regex": pat}
 
# OpenAI（JSON Schema の pattern）
{"type": "string", "pattern": f"^{pat}$"}
 
# 先読みを足した版は vLLM=400エラー / OpenAI=400エラー（以前は黙って無視）で効かない
# r"^(?=.*[A-Z])(?=.*[a-z])(?=.*[0-9])(?=.*[!@#$%])[A-Za-z0-9!@#$%]{8,16}$"

形式は守るが、中身は保証されない

形式が正しくても、中身が正しいとは限りません。

  • 「今日は何日？」に日付形式を強制 → 1811-11-07（形式は完璧、でも1811年）
  • 「日本の首都は？」に [A-Z]{20} を強制 → WEIGHINGUERSSEENINGG

後者が象徴的です。正規表現は「大文字20文字」しか要求していないので、モデルは意味を捨ててでも形式を満たしにいきます。「東京」と答えたくても、その形式では答えられないからです。

制約が"考える力"を奪ったり奪わなかったり

Qwen に 473 × 588 を計算させ、答えを \d{1,7}（数字だけ）で強制しました。結果は 1000000。まるはずれです。一方、制約を外して自由に解かせると、途中式を書いてから 278124（正解）を返しました。どうやら正規表現の制約が、Qwen の推論（reasoning）トークンの出力にまで干渉してしまうようです。推論部分を使えるよう「自由に書いてよい区間＋最後だけ 答え: \d+」のような形にすると、Qwen でも推論と形式を両立できました。

Qwen は答える前に推論のテキストを出すのですが、いきなり数字だけを強制すると、推論を書く余地がまるごとなくなってしまうようです。

5.6-sol にも同じ「数字だけ」を強制して、同じ問題を解かせてみました。結果は12回中12回正解。しかも推論を完全にオフにした設定（推論トークン0を確認済み）でも正解でした。このくらいの計算なら、推論のテキストなしで一発で答えられるようです。

6.1-sol は推論をオフにできないので、推論は low のままですが、6回中6回正解（推論トークンは13〜18）でした。小型の luna も、推論オフ（推論トークン0）で6回中6回正解しています。

強い思い込みは、正規表現でも温度でも動かない
「0〜9のランダムな数字を1つ」と頼むと、Qwen はほぼ毎回7を選びます。生の確率で0.8ほど、7に偏っています。温度（temperature）を上げると多少ばらけますが、完全に一様にはなりません。正規表現は形式を縛れても、モデルのこうした"思い込み"そのものは崩せませんでした。

これは 5.6-sol でも同様でした。5.6-sol にパスワードを30回作らせたら、30本すべての2文字目が「7」でした。6.1-sol でも30本すべて「7」です（この話は次の章で詳しく）。しかも sol は 5.6 も 6.1 も temperature を変更できない仕様なので、Qwen のように温度でばらけさせる逃げ道もありません。

この偏りは、次の電話番号の話でもっとはっきり出ます。

通常の構造化出力（JSON Schema）との比較

ここまでの問題点を並べていて、ふと思いました。電話番号やパスワードくらいなら、そもそも正規表現を使わなくてもよかったのでは、と。

気になって、Qwen に電話番号を正規表現なしで100回作らせてみました。今回は100回とも、妥当な形式の電話番号が返ってきました。番号以外の説明が混ざることもなく、桁数もあっています。比較で OpenAI の gpt-5-mini でも試しましたが、こちらも100回とも形式は正しかったです。少なくとも「架空の電話番号」に関しては、正規表現をかけなくても形式はほぼ守られていました。精度の面では、正規表現の出番があまりなかったことになります。

むしろ正規表現をかけて困る場面もありました。番号を携帯だけに絞る正規表現をかけたところ、100回中97回が 090-1234-5678 に集中してしまったのです。正規表現なしのとき（まだ固定電話などが混ざっていました）より、かえって偏りが強まりました。そして gpt-5-mini も同じ 090-1234-5678 に偏ります。この定番番号への偏りは、特定のモデルの癖というより、学習データ由来の共通の思い込みのように見えます。正規表現でどうにかできる話ではなさそうでした。

6.1-sol と luna でも、同じプロンプトで100回ずつ作らせました。

形式は4条件とも100回すべて正しく、偏りはここでも強く出ました。6.1-sol は正規表現なしでも 090-0000-0000 と 03-0000-0000 の2種類しか出さず、携帯に絞る正規表現をかけると100回すべて 090-0000-0000 です。Qwen や gpt-5-mini は 090-1234-5678、6.1-sol は 090-0000-0000 と、偏る先はモデルで違っても、1つの番号に張り付く点は同じでした。

ちなみに「正規表現をかけると、条件を守れる無難なパターンばかりになるのでは」とも思ったのですが、Qwen のデータではそうなりませんでした。番号や文字列のばらけ具合は、正規表現のあり/なしでほとんど変わりませんでした。単調さの主な原因は、正規表現よりもプロンプトと温度のほうにあったようです。

パスワードでも似た感じでした。Qwen で、8〜16文字・大小英字・数字・記号・連続禁止…といった条件をすべて満たせた割合は、こうなりました（各100回）。

  • 正規表現なし … 90%
  • 正規表現あり … 99%

差の9ポイントは、ほぼ「長さ」だけでした。正規表現で書けなかった「各種1文字以上」や「同じ文字を連続させない」は、実は正規表現なしでもモデルがほとんど満たしていて、正規表現が実際に足していたのは、ほぼ「8〜16文字」という長さの保証でした。

ちなみに 5.6-sol に同じ条件で正規表現なしのパスワード生成をさせると、30回中30回、全条件を満たしました（100%）。6.1-sol も30回中30回、luna は30回中29回です。sol くらいのモデルになると、形式の正しさはプロンプトで頼むだけでほぼ達成されてしまいます。

実際、正規表現でやっていたことの多くは、普通の構造化出力でも書けます。たとえば感情分類。正規表現なら選択肢を並べて書きます。

python
"structured_outputs": {"regex": "(ポジティブ|ネガティブ|中立)"}

これは JSON Schema の enum で同じことができます。

json
{
  "type": "object",
  "properties": {
    "sentiment": { "type": "string", "enum": ["ポジティブ", "ネガティブ", "中立"] }
  },
  "required": ["sentiment"]
}

enum は JSON Schema の標準機能で、OpenAI の構造化出力でも使えます。「決まった選択肢から選ばせる」だけなら、正規表現を持ち出さなくても、クローズドなモデルで同じことができてしまいます。電話番号のように「だいたいの形式でよい」場合も、{"type": "string"} のフィールドを1つ用意してプロンプトで形式を伝えるだけで、今回はほとんど崩れませんでした。

ただし、多様性は別問題

成功率だけ見ると、sol にプロンプトで頼めば十分に見えます。ただ、多様性は別でした。

さきほどのパスワードを、モデルごとに全部並べるとこうなっていました。

5.6-sol の30本は、全条件を満たしてはいるものの、

  • 2文字目は30本すべて「7」
  • 使われている数字はほぼ「7・2・9」だけ
  • 30本中14本が「G」で始まる

文字列としては28種類あるのに、実質は G7m@2Q…9… という1つの型の微修正です。4章で見た「7の思い込み」が、気づかないうちにパスワード全体に及んでいました。

6.1-sol も同じでした。正規表現のあり/なしにかかわらず、2文字目は60本すべて「7」、60本すべてに数字の「7・2・9」が入っていて、型が R7$mQ2!vN9@… に変わっただけです。そして sol は 5.6 も 6.1 も temperature を変更できないので、この張り付きから抜け出す手段がAPI上ありません。

一方 Qwen は、温度を1.5〜2.0まで上げるとパスワードのばらつきが大きく増えました（100本中75〜84種類）。温度を設定できることは、ローカルの地味だけど確かな利点のようです。

ここまで来て、正直こう思いました。選択肢（enum）や、対応環境での pattern で足りる場面は多い。電話番号やパスワードの生成程度であれば、正規表現による制約をあえて持ち出す必要性は薄いように感じられました。

正規表現の制約が真価を発揮するケース

正規表現が有効だったのは、こういう場面でした。enum や型指定では書けず、しかもモデルが自力では守れない構造。ここでいう「書けない」は、JSON Schema の構造キーワード（type・enum・required など）で表現できない、という意味です。JSON Schema の pattern なら書けますが、それは正規表現そのもの、つまりこの記事の主題です。

使える文字が減っていくしりとり

こんな特殊ルールのしりとりを考えました。普通のしりとり（前の単語の最後の文字で継ぐ、「ん」で終わると負け）に、ルールを1つ足します。一度つなぎ目に使った文字は、以降どこにも使えなくなる。「あ」→「あすか」→「か」…と進むと、「あ」も「か」も封印されていく。ターンごとに使える文字が1つずつ減っていくしりとりです（濁点・半濁点は清音として扱いました）。

このルールは enum や型指定では書けません。ターンごとに「今使える文字」が変わるからです。選択肢を並べる enum で書こうとすれば、毎ターン辞書18万語から合法な語だけを抽出して数千語を流し込むことになり、スキーマの上限にも引っかかって現実的ではありません。正規表現なら、毎ターン「開始文字＋今使える文字だけ＋末尾はん以外」の形で組み直すだけで済みます。答えを列挙するのではなく、ルールをそのまま書けるということです。

python
# 数ターン経過後の状態:
#   継ぐ文字 = 「り」 / つなぎ目に使って封印済み = あ・か・き・し・め
# 禁止文字ではなく「まだ使える文字」の側を毎ターン組み直す
usable   = "いうえおくぐけげこごさざすずせぜそぞただちぢつづてでとどなにぬねのはばぱひびぴふぶぷへべぺほぼぽまみむもやゆよらるれろわをん"
usable_e = usable[:-1]  # 末尾用は「ん」を除く（末尾んは負け）
pat = f"[り][{usable}]{{0,4}}[{usable_e}]"  # 全長2〜6
 
# vLLM
body["structured_outputs"] = {"regex": pat}
 
# OpenAI（JSON Schema の pattern）
{"type": "string", "pattern": f"^{pat}$"}

単語が実在するかどうかは、辞書（JMdict）から作った普通名詞リスト約18万語との照合で判定しました。しりとりの標準ルールに合わせて、動詞・形容詞・固有名詞は不可です。

結果はこうなりました。

（Qwenは各20ゲーム、5.6-solは5〜10ゲーム、6.1-sol・lunaは各10ゲーム。開始は「あ」、40手で打ち切り）

正規表現なしだと、どのモデルも最後は反則で終わります。崩れ方には差があって、Qwen は禁止文字を使ったり「ん」で終わったりと基本ルールから崩れるのに対し、5.6-sol と 6.1-sol が踏んだのは「いま継いだ文字は、その語の中でもう使えない」という一番ややこしい細則だけでした。luna はその中間で、禁止文字と細則の両方を踏んでいます。それでも、増えていく制約を最後まで追いきれない点は同じです。

正規表現ありだと、どのモデルも反則はゼロになります。そして負けの理由が、どれも同じものに揃いました。「辞書にない語」です。

伸び方にはモデルの差が出ました。6.1-sol は平均10.8手から34.3手へ大きく伸び、10ゲーム中5ゲームが打ち切りの40手まで続きました。一方 luna は、正規表現ありのほうが短くなっています（11.4手→9.1手）。10ゲームすべてが、辞書にない語での負けでした。

Qwen の最長はこの17手でした。

ひらがなの五七五

もう一つは俳句です。ひらがなで五・七・五。音を数えるのは、LLMがわりと苦手にしていることでした。

（各40句。「意味が通るか」は別のモデルに判定させました）

Qwen は正規表現なしだと12.5%しか5-7-5になりません。多くは中七が9音や10音に膨らみます。正規表現で「1音を1つの単位として、5回・7回・5回」と書けば、当然ながら100%になります。面白いのは品質のほうで、正規表現のあり/なしでほぼ変わらず3割ほど。構造を強制しても質が落ちるわけではなく、結果として「5-7-5かつ意味も通る」の両立は4倍以上になりました。差はまるごと「構造」から来ています。

python
# ひらがな＋濁点・半濁点・長音ー
kana = "あいうえおかきくけこさしすせそたちつてとなにぬねのはひふへほまみむめもやゆよらりるれろわをんがぎぐげござじずぜぞだぢづでどばびぶべぼぱぴぷぺぽー"
mora = f"[{kana}][ゃゅょ]?"   # 拗音(ゃゅょ)は直前の音にくっつけて1音と数える
pat  = rf"(?:{mora}){{5}}\n(?:{mora}){{7}}\n(?:{mora}){{5}}"  # 5音・7音・5音の3行
 
# vLLM
body["structured_outputs"] = {"regex": pat}
 
# OpenAI（改行を含む → grammar）
{"type": "grammar", "syntax": "regex", "definition": pat}

一方 sol は、正規表現なしでも40句すべてが5-7-5でした。6.1-sol と luna も同じで、判定役のモデルもほぼ全句を意味が通ると判定しました。音数勘定くらいなら、モデルの地力でカバーできてしまうようです。

ただし、句の中身は似たものばかりでした。5.6-sol は1行目が40句中34句「はるかぜや」。6.1-sol は正規表現なしだと「はるのかぜ」「あきのかぜ」「はるかぜや」に散ったものの、正規表現ありでは40句中32句が「はるかぜや」でした。luna は正規表現のあり/なしとも、36〜37句が「はるのかぜ」です。句そのものの種類も、クローズドの3モデルは40句中21〜31種類で、同じ句がそのまま何度も出てきます（Qwen は40句すべて別の句でした）。5章で見た張り付きは、ここでも健在です。

とはいえ、Qwen の正規表現ありの句の3分の2は、5-7-5でも俳句になっていませんでした。

  • さくらちる / はなみはわすれ / さくらちる（5-7-5で、意味も通る）
  • さくらびら / めだちかぞえて / はるやまに（5-7-5だが、「さくらびら」から怪しい）

しりとりと同じで、正規表現が保証するのは形式までで、中身の良し悪しまでは保証しません。

失言半減質疑応答(週刊少年ジャンプ「暗号学園のいろは」より)

濁点・半濁点は清音として使える、当て字ルビも芸のうち、というルールです。

使える音の集合はお題ごとに変わりますが、スキーマは毎回スクリプトで組み直せばよいので、それ自体は障害になりません。書けないのは中身のほうです。23音で作れる一文は無限にあるので、enum で候補を並べるという逃げ道がありません。しりとりと同じで、文字単位のルールとして書くしかない構造です。46文字から23文字をランダムに引いて、16作品（スターウォーズ、千と千尋の神隠し、ブレードランナーなど）を詠ませました。出力は「よみ」と「かんじ」の2欄に分け、音の実体である「よみ」だけを正規表現で縛ります。採点は2つ。よみが23音に収まっているか（機械判定。句読点や記号は音に数えません）と、かんじの読みがよみと対応しているか（こちらは別のモデルに判定させました）。

    "type": "object",
    "properties": {

        "yomi":  {"type": "string", "pattern": f"^{pat}$"},     # ← ここだけ許可音に制約

    "required": ["draft", "yomi", "kanji"], "additionalProperties": False,

結局、正規表現はどのような場面で有効なのか

今回試した範囲では、答えは結局モデルの強さで変わりました。

Qwen のようなローカルLLMにとって、正規表現は「できないことを可能にする」道具でした。累積ルールのしりとりも五七五も、自力ではほぼ守れず、正規表現を付けてはじめてゲームとして成立します。ただし限界もあって、いろは歌では正規表現を付けても、音は合法でも読みの対応した一文にはなりませんでした。保証できるのは形式まで、その先は地力です。

sol のように自力で形式をほぼ守れるモデルにとっては、「だいたいできることを、必ずできるに変える」保証でした。自力でもかなり守れます（俳句は40句すべて5-7-5でした）が、それがずっと続く保証はありませんし、しりとりでは明確な上積み（5.6-sol で8.0→10.4手）もありました。いろは歌でも、5.6-sol は合法率を16作品中7から16に引き上げ、合法かつ読み対応の成功率を6作品から14作品へと倍以上に伸ばしています。1件も外せない実運用なら、sol にも制約を掛ける意味はありそうです。

6.1-sol では、お題によって結果が分かれました。いろは歌は正規表現なしでも16作品すべてが合法かつ読み対応で、正規表現を付ける余地がありませんでした。一方しりとりは、正規表現なしの10.8手が正規表現ありで34.3手になり、上積みは 5.6-sol（+2.4手）よりむしろ大きくなっています。モデルが新しくなると、正規表現が要らなくなるお題と、上積みが大きくなるお題に分かれました。

小型の luna は、Qwen と sol の中間でした。正規表現を付ければ音や文字のルールは必ず守りますが、いろは歌では「よみ」と「かんじ」がずれる作品が残り、しりとりでは正規表現ありのほうが短く終わっています。

逆に、電話番号やパスワードのように、モデルが自力でだいたい形式を守れて、しかも普通のスキーマで書ける場面では、どのモデルでも正規表現の出番はそれほどありませんでした。

そして最後まで変わらなかったのは、正規表現は形式を保証しても、中身（実在する単語か、良い俳句か、正しい答えか）はモデル任せ、ということでした。中身と多様性はモデルとサンプリング設定の領分。形式は正規表現の領分。この役割分担が、今回の検証の結論です。

補足：pydanticでも正規表現でバリデーションできるのでは？

「pydanticの Field(pattern=...) でも正規表現チェックできるよね？」と思った方もいるかもしれません。できます。ただ、役割が少し違います。

pydantic の Field(pattern=...) は、後処理のバリデーションです。モデルが出力した"後"に検証し、合わなければ例外を出す/やり直す。つまり不正な出力は、一度は作られます。

制約付きデコードは、生成のその場で不正なトークンを禁止します。だから不正な出力は、そもそも作られません。「書いてから校正して直す」のか、「そもそも不正な字が打てないキーボードを使う」のか、という違いです。vLLM の structured_outputs も、2章で出てきた OpenAI の pattern と grammar も、この「事前」型です。
